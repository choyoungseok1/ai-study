# 멀티홉 Agentic RAG

HotpotQA의 멀티홉 질문을 ReAct 루프로 분해해 검색하는 시스템. 단일 검색 RAG로는 도달할 수 없는 문서에 에이전트가 도달하는지를 recall로 정량 검증한다.

핵심 질문은 "에이전트가 더 잘하는가"가 아니라 **"더 잘하는 게 능력 때문인가 예산 때문인가"** 다. 에이전트는 검색을 여러 번 하므로 자연히 더 많은 문서를 본다. 그 차이를 통제한 비교가 이 프로젝트의 중심이다.

---

## 결과

bridge 질문 검색 recall@k (n=37). 단일 검색에 Agentic과 같은 문서 예산을 줬을 때:

| | recall@k |
|---|---|
| 단일 검색 (k=8.1) | 0.703 |
| Agentic 멀티홉 | 0.892 |

차이는 +0.189, 95% 신뢰구간 [0.101, 0.277]. 구간에 0이 없으므로 표본 우연으로 보기 어렵다.

이 값은 **재측정에서 재현됐다.** 앞선 n=47 평가에서 +0.195 [0.029, 0.361]이었고, 생성 프롬프트를 통일해 다시 돌린 n=50 평가에서 +0.189 [0.101, 0.277]이다. 차이값은 거의 그대로이고 구간 폭만 절반으로 줄었다.

### 왜 예산을 맞췄나

recall은 문서를 더 가져올수록 떨어지지 않는다. Agentic은 검색을 여러 번 하니 자연히 더 많이 본다. 이 상태로 비교하면 "많이 봐서 이긴 것"과 구분이 안 된다.

그래서 단일 검색에도 같은 예산을 줬다. 기준은 각 질문에서 **Agentic이 실제로 본 고유 문서 수**다. 전체 평균(8.7)을 일괄 적용하지 않고 질문별로 매칭했다. 홉이 3번 돌아도 재검색분이 겹치면 실제로 본 문서는 15개가 아니므로, 홉 수 × 5가 아니라 중복을 제거한 수를 썼다.

### 왜 recall인가

검색이 놓친 문서는 뒤에서 못 되살린다. 재정렬기는 후보 안에서 순서만 바꾸고, LLM은 컨텍스트에 없는 걸 근거로 쓸 수 없다. 검색 recall이 파이프라인의 상한이다.

실제로 이 코퍼스에서 상한@20은 0.869인데 재정렬 후 recall@5는 0.849였다. 1단계 검색이 못 가져온 0.131은 이후 어떤 단계로도 복구되지 않는다.

### 전체 결과

| bridge (n=37, 평균 k=8.1) | 0.662 | 0.797 | 0.703 | 0.892 |

HotpotQA dev 서브셋 500개 중 앞 50문항 **전량**. 평가 도중 tool call 스키마 오류가 1건 발생했으나(실행 51회 중 1건, 성공률 98.0%) 재시도로 회수해 결측이 없다. 별도로 무료 티어 일일 토큰 한도 소진에 의한 API 거부가 17회 있었는데, 이는 시스템 품질이 아니라 평가 운영 비용이므로 성공률 분모에서 제외했다.

</details>

### 읽을 만한 지점 두 개

**재정렬이 예산 늘리기보다 낫다.** bridge에서 rerank는 0.797, pure_budget은 0.703이다. 재정렬은 문서 5개만 LLM에 주고 pure_budget은 평균 8.1개를 준다. 적게 주면서 더 잘한다. 후보를 넓히는 것보다 순위를 정확히 하는 쪽이 효율적이라는 뜻이다.

**comparison에서 Agentic은 이득이 없고 비용만 더 쓴다.** recall이 pure_budget과 완전히 같은 0.923인데, 홉은 평균 2.69회로 bridge(1.92)의 1.40배이고 컨텍스트에 들어간 고유 문서는 10.7개로 1.33배다. 13문항 중 12개가 다홉으로 갔다 — 두 엔티티가 질문에 모두 등장해 한 번에 뽑을 수 있는데도 굳이 분해했다.

**반면 bridge에서는 홉 배분이 난이도를 따라간다.** 단일 검색이 잘 듣는 질문(pure 0.706)에서는 46%가 1홉에 종료하고, 잘 듣지 않는 질문(pure 0.625)에서는 홉을 늘린다. 그리고 홉을 늘린 쪽에서 단일 검색 대비 격차가 더 크다(+0.300 vs +0.147). 필요한 곳에 더 쓴다는 뜻이다.

**즉 난이도 적응은 되는데 유형 적응은 안 된다.** 사후 판단(1홉 돌려보고 부족하면 더 간다) 방식의 구조적 한계다. 질문 유형은 실행 전에 판별해야 하는 정보인데, 실행해봐야 아는 구조에서는 잡히지 않는다. 사전 복잡도 분류기를 두는 접근이 겨냥하는 지점이 정확히 여기다.

## 정답률

recall이 오르면 정답도 오르는가. 별개 축이므로 따로 측정한다.

**Agentic의 우위는 검색 회수율에서 온다.** 세 모드의 EM을 gold 회수 여부로 조건부 분해하면, 조건부 정답률(gold를 다 잡았을 때 맞히는 비율)은 세 모드가 비슷하다. 차이를 만드는 것은 gold 회수율 자체다. 즉 Agentic이 답을 더 잘 만드는 것이 아니라 답의 재료를 더 잘 가져온다.

**gold를 절반만 잡으면 사실상 실패다.** gold 2/2를 잡았을 때와 1/2만 잡았을 때의 정답률 격차가 크다. 멀티홉 질문에서 recall 0.5는 "절반의 성공"이 아니라 실패에 가깝다.

**어려운 구간에서는 병목이 검색이 아니다.** bridge를 홉 수로 나눠 보면:

| bridge | n | agentic recall | agentic EM | pure recall |
|---|---|---|---|---|
| 1홉 종료 | 17 | 0.853 | 0.706 | 0.706 |
| 2홉 이상 | 20 | 0.925 | 0.350 | 0.625 |

2홉 이상 구간은 검색을 **더 잘했는데** 정답률이 절반이다. 검색이 완전히 성공한 경우만 놓고 봐도 조건부 정답률이 1홉 구간보다 낮다.

⚠️ 이를 "홉을 많이 쓰면 답이 나빠진다"로 읽으면 인과 방향이 뒤집힌다. 같은 표에서 pure recall도 0.625로 낮다 — 애초에 어려운 질문들이고, **어려워서 홉을 더 쓴 것**이다. 방어 가능한 서술은 이쪽이다: 검색 축에서는 목표를 달성했고(2홉+ recall 0.925), 남은 손실은 여러 문서를 엮어 추론하는 단계에 있다. 이 부분은 검색 개선으로 풀리지 않는다.

⬜ *단일 검색에 k=50을 주면 recall은 Agentic 수준에 근접한다(아래 recall 곡선). 그때 EM도 따라오는지는 측정 예정.*

## 왜 Agentic인가

bridge 질문의 정답 문서 중 일부는 **원 질문으로 검색해서 나올 수 없다.** 질문에 그 문서를 가리킬 식별자가 없기 때문이다.

실제 사례 (idx=2):

> Q: "Dave Hemingway와 'A Little Time'을 듀엣한 가수는 어느 나라 출신인가?"
>
> gold: `A Little Time`, `Briana Corrigan`

원 질문으로 top-20을 뽑으면 `A Little Time`은 1위로 잡히지만 `Briana Corrigan`은 **20위 안에 없다.** 질문에 그 이름이 등장하지 않으므로 이 질의로는 도달할 수 없다. k를 100으로 키워도 마찬가지다. 순위 문제가 아니라 질의가 그 문서를 가리키지 못하는 문제다.

에이전트는 1홉에서 `A Little Time` 문서를 읽고 듀엣 상대가 누구인지 알아낸 뒤, 2홉에서 그 이름으로 검색해 도달한다. 에이전트의 가치는 같은 검색을 여러 번 하는 것이 아니라 **이전 관찰 결과로 새 검색어를 생성하는 것**이다.

### 주장의 범위

k를 늘리면 일부 케이스는 잡힌다. bridge에서 k를 5에서 평균 8.1로 올렸을 때 recall이 0.662에서 0.703으로 +0.041 올랐다. 그러나 Agentic의 0.892에는 미치지 못하고 +0.189가 남는다. 격차의 대부분은 순위 문제로 설명되지 않는다.

<details>
<summary>초기 n=10 실험에서 이 주장을 과대평가했던 기록</summary>

n=10에서는 k를 2배로 올려도 10문항 전부 recall 변화가 0이었고, 이를 "k를 늘려도 전혀 잡히지 않는다"는 증거로 삼았다. n=47로 확대하니 +0.069, n=50 재측정에서 +0.041로 올랐다. 작은 표본에서 나온 "완벽한 0"은 신호가 아니라 표본 부족의 징후였다. 수정된 주장은 "k 증가가 부분적으로 도움이 되지만 격차를 메우지는 못한다"이다.

</details>

## 아키텍처

```
질문
 │
 ├─ 검색 (bi-encoder, all-MiniLM-L6-v2)          top-20
 │        │
 │        └─ 재정렬 (cross-encoder, bge-reranker-base)  top-5
 │
 ├─ 에이전트 (ReAct 루프, Groq function calling)
 │        관찰 → 새 검색어 생성 → 재검색 (최대 6홉)
 │
 ├─ 평가 (recall@k, EM/F1, context_precision)
 │
 └─ 서빙 (FastAPI, 3모드)   pure | rerank | agentic
```

### 설계 결정

**영어 전용 임베딩** — 코퍼스와 질문이 모두 영어인데 multilingual 모델은 384차원 공간을 50개 언어에 나눠 쓴다. 언어 간 정렬은 이 태스크에 필요 없는 능력이고, 그 대가로 영어 의미 구분에 쓸 표현 용량이 줄어든다. recall@5가 0.57에서 0.739로 올랐다. multilingual이 레이어 2배, 파라미터 5배인데도 더 나빴다.

**2단계 검색** — bi-encoder는 질문과 문서를 따로 인코딩해 빠르지만 둘의 관계를 보지 못해 순위가 거칠다. cross-encoder는 함께 읽어 정밀하지만 코퍼스 전체에 쓰면 질문당 4928회 forward가 필요하다. bi로 20개 추리고 cross로 재정렬해 절충했다 (0.739 → 0.849).

**open-domain 검색** — HotpotQA는 질문마다 후보 문단 10개를 제공하지만 전체 코퍼스 4928개를 인덱싱했다. 후보가 10개면 정답이 애초에 그 안에 있어서 "검색으로 도달 불가능한 문서"라는 개념이 사라지고, 이 프로젝트가 측정하려는 대상도 함께 사라진다. 대가로 recall 절대값이 낮다 (상한@20 = 0.869).

**LangChain 미사용** — ReAct 루프를 raw Groq SDK로 직접 구현했다. request → execute → respond 왕복을 손으로 짜면 tool calling의 전체 메커니즘이 드러나고, 추상화가 감추는 버그를 피할 수 있다.

## 평가 지표

recall@k와 context_precision을 **합치지 않고 병렬 보고**한다. 전자는 "놓친 정답이 있나", 후자는 "가져온 것 중 쓸모없는 게 많나"에 답한다. 가중합으로 뭉개면 두 지표가 서로 다른 방향을 가리킬 때의 정보가 사라진다.

<details>
<summary>context_precision을 LLM judge로 구현했고, 그 한계를 규명한 기록</summary>

RAGAS 대신 judge를 직접 호출했다. 0.4.x에서 API가 크게 바뀌어 안정화 시간이 불확실했고, judge 호출을 직접 통제해야 Groq의 `n=1` 제약과 rate limit을 회피할 수 있었다. 로직이 단순해 직접 구현하는 편이 "이 숫자가 어떻게 나왔는지"를 코드로 설명할 수 있다.

판정 결과를 육안 검수하다 문제를 발견했다. judge가 **gold 문서를 무관으로 판정**했다. 위 사례의 `A Little Time`이 그렇다. 듀엣 상대를 알려주는 bridge 문서인데, 프롬프트에 "intermediate step도 유용하면 yes"를 명시했음에도 judge가 질문을 표면적으로만 보고("국적 정보가 없으니 무관") 걸러냈다.

gold 문서를 자동 relevant로 고정하자 이번에는 지표가 recall의 변형으로 붕괴했다. bridge 세 비교군이 0.33 부근으로 수렴했다. 사실상 `gold 잡은 수 / 검색한 수`가 되어 judge 고유의 신호가 사라진 것이다.

RAGAS 원 논문에서도 context relevance는 세 지표 중 인간 일치도가 가장 낮았고(0.70), 저자들도 긴 컨텍스트에서 핵심 문장 선별에 실패한다고 보고했다. 그리고 RAGAS는 reference-free를 전제로 설계됐다. gold 라벨이 있는 이 태스크는 논문이 상정한 조건이 아니다.

결론: **집계 절대값은 신뢰하지 않고 bridge/comparison 비대칭의 방향성만 근거로 사용한다.** comparison에서 agentic이 정밀도 손해를 본다는 결과는 두 judge 방식에서 모두 일관되게 나타났다.

</details>

### 알려진 한계

**평가가 완전히 재현되지 않는다.** 에이전트의 검색어는 LLM이 생성하는데 temperature를 고정하지 않았다. 같은 질문에 홉별 검색어가 실행마다 달라지므로 같은 평가를 다시 돌리면 숫자가 미세하게 움직인다. 위 신뢰구간은 질문 간 분산만 반영하고 **실행 간 분산은 포함하지 않는다.**

temperature 0으로 고정하면 재현성은 얻지만 에이전트가 막혔을 때 다른 검색어를 시도할 여지가 사라진다. 실제로 이번 평가에서 tool call 스키마 오류로 실패한 질문이 코드 수정 없이 재시도만으로 성공했는데, 이는 비결정성이 오류 복구로 작동한 사례다. 재현성 · 탐색 다양성 · 오류 복구가 한 축에 얽혀 있어 단순히 고정하는 것이 답은 아니다.

⬜ *실행 간 편차 실측 예정 (동일 조건 재실행 1회).*

**tool calling 성공률 98.0%.** `gpt-oss-120b`가 스키마에 없는 인자를 생성하는 경우가 실행 51회 중 1건 있었다(`query` 누락, `cursor`/`id` 생성). 실패를 `error` 필드로 격리해 평균 오염을 막고, 이어하기에서 재시도해 회수했다.

<details>
<summary>이어하기 로직에 있었던 버그</summary>

완료 판정 함수가 `error` 레코드까지 "완료"로 세고 있었다. 일일 토큰 한도로 죽은 질문들이 재실행 시 영구히 건너뛰어져, 이어하기가 실제로는 동작하지 않았다. 에러가 발생하지 않으므로 발견이 늦었다. `error is None`인 레코드만 완료로 세도록 고치고, 재시도로 같은 인덱스가 중복되므로 레코드 병합은 나중 것이 이기도록 했다.

</details>

**comparison에서 분해가 손해다.** 두 엔티티가 질문에 모두 있는데 불필요하게 쿼리를 분해하면 원 질문이 잡던 문서를 놓칠 수 있다. 개별 사례로 확인되고(단일 검색보다 문서를 더 보고도 recall이 낮은 케이스), 집계로는 recall 이득 0에 비용 초과로 나타난다. 다만 comparison n=13이라 "이득이 없다"까지만 말할 수 있고 "평균적으로 손해다"는 표본이 부족하다.

**recall ≠ 정답률.** gold 문서를 놓쳤는데도 LLM의 파라메트릭 지식으로 정답이 나오는 경우가 있다. 이 코퍼스는 closed-domain이므로 무검색 경로를 두지 않았으나, 에이전트가 1홉에서 조기 종료하는 질문들에는 같은 오염이 남아 있을 수 있다.

projects/multihop-agentic-rag/

실험은 노트북에서, 굳은 것은 `src`로 옮긴다. 평가 로그는 JSONL로 append하며 원본만 저장한다. 홉 수나 고유 문서 수 같은 파생값은 분석 시점에 계산한다. 집계값을 저장하면 정의가 바뀔 때 전체를 재실행해야 한다.

## 실행

```bash
pip install -r requirements.txt

# .env 설정
GROQ_API_KEY=...
CHROMA_DIR=C:\path\to\chroma    # ASCII 경로여야 함 (아래 참고)

python -m src.retrieve    # 코퍼스 인덱싱 (CPU, 약 2분)
python -m src.agent       # 비교군 평가 (이어하기 지원)
python -m scripts.eval_stats   # 평가 로그 통계

uvicorn app.main:app --reload  # 서빙
```

```bash
curl -X POST localhost:8000/ask \
  -H "Content-Type: application/json" \
  -d '{"question": "...", "mode": "agentic"}'
```

응답에 `retrieved_titles` · `hops` · `search_log` · `elapsed_ms`를 함께 반환한다. 평가가 차별점인 프로젝트이므로 답변만이 아니라 검색 경로가 보여야 한다. `search_log`는 "왜 Agentic인가"의 라이브 데모이기도 하다 — 1홉 결과에 없던 엔티티가 2홉 검색어가 되는 과정이 그대로 찍힌다.

모델 로딩은 요청 시점이 아니라 `lifespan`에서 1회 수행하고, 기동 시 워밍업 쿼리를 던진다. 인덱스 로드 실패를 첫 요청의 500이 아니라 startup 에러로 드러내기 위해서다.

`python 경로/파일.py`가 아니라 `python -m src.모듈`로 실행해야 한다. 전자는 `sys.path[0]`이 파일이 있는 폴더가 되어 `from src.X import Y`가 실패한다.

`CHROMA_DIR`은 ASCII 경로로 지정한다. 비ASCII 경로에서는 chroma-hnswlib(C++ 확장)이 인덱스를 로드하지 못한다. sqlite를 읽는 `count()`는 통과하는데 hnsw를 읽는 `query()`만 실패하는 비대칭이 단서였다.

**범위에서 뺀 것**

- *정체 감지* (홉 간 새 문서가 0개면 조기 종료) — 설계까지 했으나 제외했다. 최초 근거는 "정체가 성능을 깎는다"였는데, 데이터를 다시 보니 인과가 반대였다. 최대 홉에 도달한 질문이 저성능인 게 아니라 **저성능이라서 오래 탐색한 것**이다. 정체 감지는 recall이 아니라 비용을 줄이는 축이고, 이 프로젝트의 측정 대상이 아니다.
- *vLLM 서빙* — Linux 전용이고 로컬 GPU가 2GB라 실측이 불가능하다. 실행해보지 않은 것을 넣지 않았다. FastAPI + provider 추상화로 대체하고, 어댑터를 추가하면 붙는 구조로 남겨뒀다.
