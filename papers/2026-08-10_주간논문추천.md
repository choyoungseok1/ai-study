## 1. Dissecting Agentic RAG: A Component Ablation for Multi-Hop QA with a Local 7B Model ⭐ 최우선

**arXiv**: https://arxiv.org/abs/2606.21553 (2026년 6월) · **코드**: https://github.com/sherozshaikh/agentic-rag-eval

**초록 (요약)**
Agentic RAG는 반복 추론 루프, 질의 분해, 적응형 검색을 결합해 멀티홉 QA를 다룬다. 이 논문은 HotpotQA distractor dev 5,000문항에서 로컬 Qwen2.5-7B-Instruct로 전체 agentic RAG 파이프라인을 평가해 EM 53.2% / F1 61.6%를 얻었고, 단일 패스 dense 검색 베이스라인(EM 43.1% / F1 54.0%)과 비교한다. 8가지 ablation 조건에서 (1) RRF(reciprocal rank fusion) 기반 **고정** 하이브리드 검색이 규칙 기반 **적응형 라우팅**을 일관되게 능가하고, (2) 검색 반복 2회가 5회 이득의 95%를 확보하며 더 깊은 루프는 유의미한 이득이 없고, (3) 질의 분해와 cross-encoder 재정렬은 각각 통계적으로 유의하지만 더 작은 이득을 낸다는 것을 밝힌다. 결론: **단순하고 고정된 선택이 적응형 버전과 대등하거나 더 낫다.**

**추천 이유 3줄**
1. 오늘 할 일인 "Adaptive-RAG 2Wiki 정정"에 대한 직접적인 독립 증거다 — "적응형 라우팅이 고정 하이브리드보다 못하다"는 결론은 8/6에 본인이 발견한 Table 4 역전(분류기 정확도 최고 = QA F1 최저)과 같은 방향을 가리킨다. 논문 하나의 특이 결과가 아니라는 근거가 생긴다.
2. 실험 설정이 본인 프로젝트와 거의 동일하다(HotpotQA distractor, EM/F1, 비교군 = 단일 패스 dense vs agentic, cross-encoder 재정렬 포함). 숫자를 그대로 옆에 세워 비교 가능하고, 코드도 평가 스크립트 위주라 읽는 부담이 적다.
3. "반복 2회가 5회의 95%"는 agentic 13.4s(pure 대비 45배) 지연 문제에 대한 즉시 적용 가능한 답이다 — 이번 주 Groq TPD 제약 하에서 실험 없이 홉 수 상한을 정당화하는 근거로 쓸 수 있다.

**분량**: 본문 7절 + 참고문헌 구조, 단독 저자 실증 논문 — 10페이지 내외로 추정 (정확한 페이지 수는 arXiv 메타에 미기재)

## 2. RAG-X: Systematic Diagnosis of Retrieval-Augmented Generation for Medical Question Answering ⭐

**arXiv**: https://arxiv.org/abs/2603.03541 (2026년 3월)

**초록 (요약)**
기존 RAG 평가 벤치마크는 단순 객관식 QA에 집중하고, 복잡한 QA가 요구하는 의미적 정밀도를 제대로 포착하지 못하는 지표를 쓴다. 무엇보다 **오류가 검색 실패에서 왔는지 생성 실패에서 왔는지 진단하지 못해** 타깃 개선이 불가능하다. RAG-X는 검색기와 생성기를 독립적으로 평가하는 진단 프레임워크로, 정보 추출 / 단답 생성 / 객관식 세 과제에 걸쳐 측정한다. **CUE(Context Utilization Efficiency)** 지표를 도입해 시스템 성공을 해석 가능한 사분면으로 분해하고, 검증된 근거 기반 성공과 "속임수 정확도(deceptive accuracy)"를 분리한다. 실험 결과 인지된 시스템 성공과 근거 기반 성공 사이에 **14% 격차("Accuracy Fallacy")**가 존재한다.

**추천 이유 3줄**
1. 본인이 8/6에 직접 만든 것과 같은 물건이다 — `answer_eval.py`의 cross_table 3분류, "gold 못 잡았는데 정답"(qa[18]), 조건부 정답률 P(정답|2/2) 분해가 정확히 CUE 사분면·Accuracy Fallacy의 문제의식이다. 자기 발견에 표준 용어와 인용 가능한 출처가 붙는다.
2. 면접 방어 카드 '인과 분해'를 가장 강한 항목으로 꼽아 두셨는데, "이건 제가 임의로 만든 표입니다"와 "RAG-X의 CUE 사분면과 같은 프레임입니다"는 설득력이 다르다. 8/12 방어 노트 정리에 그대로 들어간다.
3. 예상 반박("P(정답|2/2)에서 pure가 1위면 pure 생성이 더 나은 것 아니냐" → 선택 편향)에 대해, 이 논문이 같은 함정을 어떻게 처리하는지가 반박 대응의 2차 근거가 된다.

**분량**: 짧은 진단 프레임워크 논문 — 8~10페이지 추정
**⚠️ 코드**: 초록에 공개 명시 없음. 저장소 확인이 안 되어 "코드 공개 우선" 기준에는 미달할 수 있음 — 읽을 가치가 커서 포함했습니다.

## 3. Lost in the Evidence? Reproducing Document Position and Context Size Effects in RAG

**arXiv**: https://arxiv.org/abs/2605.27105 (2026년 5월, **SIGIR 2026 채택**) · **코드/설정 전량 공개 명시**

**초록 (요약)**
RAG는 검색 문서를 입력 컨텍스트에 이어 붙이므로 **문서 순서**와 **컨텍스트 크기**가 결정적이지만 논쟁적인 설계 선택이다. 선행 연구는 lost in the middle 같은 위치 효과를 보고하나, 모델·데이터셋·평가 프로토콜에 따라 결과가 일관되지 않고 재현이 어렵다. 이 논문은 통제된 평가 프레임워크에서 이 주장들을 재검증하는 체계적 재현성 연구다. 먼저 **토픽 샘플링이 분산의 주요 원인**임을 보인다 — 작은 토픽 집합은 순서 효과를 가리거나 과장한다. 반복 부분집합 샘플링으로 안정적 추세를 주는 토픽 수를 찾는 실용적 보정 절차를 제시한다. 이어 현대 LLM에서 위치 민감도를 재평가하고, oracle 문서가 아니라 **실제 검색기가 관련성을 매개하는 현실적 RAG 시나리오**로 확장한다. 여기서 최근 산업계 연구를 재검토해 제한적 토픽 커버리지·LLM 판정자 의존 등 평가 선택에서 오는 불일치를 지적한다. 결론: 검색 순서와 컨텍스트 크기는 **검색 품질·모델 선택과 강하게 상호작용**하며, 이상화된 설정의 결론은 실제 파이프라인으로 항상 전이되지 않는다.

**추천 이유 3줄**
1. 8/9에 못 박아 둔 예측("k=50 pure는 recall이 비슷해도 EM은 더 낮을 것, 노이즈가 10배로 늘어서")을 정면으로 다루는 논문이다. 예측이 맞든 틀리든 채점 직후에 읽으면 해석의 언어가 생긴다.
2. "작은 토픽 집합이 순서 효과를 가리거나 과장한다"는 지적은 n=50 규모로 결론을 내고 있는 현재 실험의 정직한 한계 서술에 그대로 쓸 수 있다 — README에 '불리한 숫자 최상단' 원칙을 이미 세우셨으니 결이 맞는다.
3. LLM 판정자 의존에 대한 비판은 RAGAS judge 모델 확정(7/25)과 answer_relevancy NaN 제외 결정을 방어할 때의 근거가 된다. SIGIR 재현성 트랙이라 실험 설계 서술이 깔끔해서 읽는 속도도 빠르다.

**분량**: SIGIR 재현성 트랙 — 10~12페이지 추정

## 4. LatentRAG: Latent Reasoning and Retrieval for Efficient Agentic RAG

**arXiv**: https://arxiv.org/abs/2605.06285 (2026년 5월 7일)

**초록 (요약)**
단일 단계 RAG는 단순 QA에 효율적이지만 복잡한 질문에서 무너진다. Agentic RAG는 LLM이 검색 에이전트로서 중간 사고와 서브쿼리를 생성해 검색 시스템과 반복 상호작용하도록 확장하지만, **긴 사고·서브쿼리의 자기회귀 생성 때문에 상당한 지연**이 발생한다. LatentRAG는 추론과 검색을 이산 언어 공간에서 **연속 잠재 공간**으로 옮긴다. 토큰 단위로 자연어 사고를 생성하는 대신, 은닉 상태에서 사고·서브쿼리의 잠재 토큰을 **단일 forward pass**로 직접 만든다. LLM을 dense 검색 모델과 잠재 공간에서 정렬해 잠재 서브쿼리 토큰 위에서 검색이 가능하게 하고 end-to-end 공동 최적화를 지원한다. 투명성을 위해 잠재 토큰을 자연어로 되번역하는 병렬 잠재 디코딩을 넣었다. 7개 벤치마크에서 명시적 agentic RAG와 **대등한 성능을 유지하면서 추론 지연을 약 90% 감축**한다.

**추천 이유 3줄**
1. 8/3에 실측한 응답시간 pure 300ms / rerank 5s / agentic 13.4s(45배)가 이 논문의 문제 정의 그 자체다 — "agentic이 왜 느린가, 줄일 수 있는가"에 대한 최신 답이라 면접에서 "그 비용은 어떻게 하실 건가요"에 대응된다.
2. 다만 실제로 도입할 기법은 아니다(학습 필요, 2GB VRAM 환경 밖). **읽는 목적은 구현이 아니라 지연의 원인 분해** — 지연이 검색이 아니라 사고/서브쿼리의 토큰 생성에서 온다는 진단 자체가 방어 노트에 쓰인다.
3. Phase B(arXiv 코퍼스)는 문단이 길어 TPD 압박이 더 커지는데, 8/13에 내릴 provider 전환 판단(Gemini는 4홉 성향)의 배경 지식이 된다.

**분량**: 7개 벤치마크 실험 — 10~12페이지 추정
**⚠️ 코드**: arXiv 페이지에 저장소 링크 미기재. 코드 미공개일 가능성 있음.

## 5. A-RAG: Scaling Agentic RAG via Hierarchical Retrieval Interfaces (Phase B 참고용)

**arXiv**: https://arxiv.org/abs/2602.03442 (2026년 2월) · **코드**: https://github.com/Ayanami0730/arag (MIT, ⭐323)

**초록 (요약)**
기존 RAG는 두 패러다임에 머물러 있다 — (1) Graph RAG: 알고리즘이 한 번에 패시지를 검색해 입력에 이어 붙임, (2) Workflow RAG: 워크플로를 미리 정의하고 모델이 단계별 실행. 어느 쪽도 모델이 **검색 결정에 참여**하지 못해 모델 성능 향상에 따른 확장이 막힌다. A-RAG는 `keyword_search` / `semantic_search` / `chunk_read` 세 가지 **계층적 검색 인터페이스를 모델에 직접 노출**해, 에이전트가 여러 입도에서 적응적으로 탐색하게 한다. 진정한 agentic 자율성의 3원칙(자율적 전략 선택 / 반복 실행 / ReAct 방식의 도구 사용 교차)을 모두 만족한다. GPT-5-mini 백본에서 MuSiQue 74.1 / HotpotQA 94.5 / 2Wiki 89.7 (LLM-Acc)로 HippoRAG2·LinearRAG·GraphRAG 등을 능가하며, **동등하거나 더 적은 검색 토큰**으로 달성한다.

**추천 이유 3줄**
1. 8/15 Phase B(arXiv 도메인 논문 RAG)의 직접적 설계 참고다 — 논문 코퍼스는 청크가 길고 구조적이라 `chunk_read`(±1 인접 청크 읽기, 중복 방지 컨텍스트 트래커) 같은 인터페이스 설계가 그대로 쓸모 있다.
2. 코드 품질이 이번 목록 중 가장 좋다(MIT, provider 추상화·비용 추적 내장, `src/arag/core/llm.py`). 본인이 8/4에 만든 `LLMProvider` 어댑터와 같은 문제를 어떻게 풀었는지 대조하면 코드 리뷰 한 시간으로 얻는 게 많다.
3. 2Wiki에서 GPT-4o-mini 백본은 HippoRAG2에 지고 GPT-5-mini에서는 크게 이긴다 — **백본에 따라 순위가 뒤집히는 사례**라, "왜 Agentic인가" 방어 카드에 "모델 세대에 따라 답이 달라진다"는 뉘앙스를 추가할 수 있다.

**분량**: ⚠️ 표·벤치마크가 많아 **15페이지를 넘길 가능성이 높습니다.** 요건에 맞추려면 본문 §3(방법)과 §5(결과)만 발췌하거나, 8/15 Phase B 착수 시점으로 미루는 편을 권합니다.
