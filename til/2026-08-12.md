### 2. `compare_k50.py` — 평균끼리 빼지 않는다

22줄짜리지만 통계 설계가 들어 있다. 두 평균의 차이가 아니라 **질문별 차이의 표본분산**으로 SE를 낸다.

```python
d = [g[key] - p[key] for _, p, g in rows]      # 질문별 차이
var = sum((x - md) ** 2 for x in d) / (n - 1)  # 대응표본 분산
se = (var / n) ** 0.5
```

`eval_k50.py`의 `summarize()` 말미에도 같은 경고가 있다: *"전체 평균끼리 빼지 말 것 — 대응표본이므로 질문별 차이를 내야 신뢰구간이 나온다."*

## 배운 개념

**1. 원형 버퍼 위의 가변 크기 투 포인터** — `week17_두큐합같게만들기.py`

두 큐를 이어붙여 `A = queue1 + queue2`로 두고 창 `[l, r)`를 queue1으로 본다. 원소를 옮기는 게 아니라 창을 민다.
그런데 이 창은 **직선이 아니라 원형**이다. `r`이 `2n`에 닿아도 queue2가 빈 게 아니다 — queue1에서 pop된 `A[0:l]`이 거기 쌓여 있다. 그래서 `A[r % 2n]`.

```python
assert solution([2,7,6,6,2], [3,3,2,6,1]) == 10   # 직선 창으로는 "해 없음"
```

투 포인터가 성립하는 근거도 명시돼 있다 — **모든 원소가 양수**라서 창을 넓히면 합이 반드시 늘고 좁히면 반드시 준다. 단조성이 없으면 "크면 왼쪽, 작으면 오른쪽"이 무너진다.

**2. 반복 상한은 "시나리오"가 아니라 "변수의 최대 범위"로 잡는다**

`2n-1`이 오답인 이유가 반례와 함께 있다.

```python
assert solution([1,1,4,1,6], [1,6,5,6,3]) == 10   # 2n-1 = 9 < 10
```

올바른 유도: `l`은 원형이라 `2n` 주기로 상태가 반복되므로 `l < 2n`. 각 `l`에 대해 창은 최대 한 바퀴이므로 `r ≤ l + 2n`. 따라서 작업 수 `= l + r - n < 5n`. → **증명 가능한 상한 5n.** 실측 최악은 `ops/n ≈ 2.17`이라 3n으로도 통과하지만, 방어할 수 있는 수는 5n이다.

**3. 재계산이냐 증분이냐는 취향이 아니라 창 크기가 상수인지에 달렸다**

전날 할인 행사는 창 크기가 고정 10이라 `Counter` 재계산으로 충분했다. 오늘은 창이 최대 `2n`까지 커지므로 매번 `sum()`을 부르면 `5n × n = 4.5×10¹¹`. 같은 슬라이딩 윈도우인데 판단이 갈리는 지점이 명확하다.

**4. 대응표본 비교 — 평균의 차이 ≠ 차이의 평균**

같은 질문에 두 방법을 적용했으면 질문별 차이 `d_i`를 만들어 그 표본분산으로 SE를 낸다. 두 독립 평균을 빼면 질문 난이도의 분산이 그대로 남아 CI가 불필요하게 넓어진다.

**5. 측정 도구와 측정 대상은 같은 설정을 공유하면 안 된다**

judge를 `default_provider()`에 묶지 않은 이유. 이건 RAG 특유의 얘기가 아니라 실험 설계 일반이다.

**6. 정답지도 검증 대상이다 (신규 지침 24번)**

교차검증용 브루트포스를 `l ≤ r ≤ 2n`으로 잘라 만들었더니, **정답인 제출 코드를 "161건 불일치"로 오판했다.** 정답지 쪽에서 원형 경로를 빼먹은 것.

> *"참조 구현에 최적화·수학적 축약이 섞이면 그건 정답지가 아니라 두 번째 풀이다. 정의를 그대로 옮긴 구현만 정답지."*

최종 정답지는 `deque`로 실제로 원소를 옮기는 시뮬레이션(`solution_sim`)이고, 랜덤 20,000건 × 2회(개선본·제출본) 교차검증이 파일에 실행 가능한 형태로 붙어 있다.

## 막힌 부분

**1. 정답지가 틀렸다 — 검증 체계 자체의 실패**

`assert`를 아무리 많이 돌려도 정답지가 틀리면 신호가 반대로 나온다. "느리지만 확실한 구현을 정답지로"(지침 21번)에서 **'확실한'의 근거를 대지 않은 것**이 원인이다. 인덱스 트릭이 들어간 순간 그건 이미 최적화다.

**2. 상한을 한 시나리오로 일반화 — 이틀 연속 같은 계열**

"q1 전부 + q2 거의 전부 = 2n−1"은 특정 경로를 센 것이지 최악을 센 게 아니다. 전날 할인 행사에서 창 개수를 나눗셈으로 센 것과 구조가 같다. **반복되는 실수 유형이다.**

**3. `-1` 조건을 과하게 잡았다**

"원소가 절반보다 크면 불가능"은 참이지만 불필요하다. 상한 루프가 이미 걸러낸다. 조건을 늘리면 검증 대상이 늘고 그 조건 자체가 틀릴 위험이 생긴다.

**4. 제출본의 비대칭 — 버그는 아니지만 근거가 없다**

```python
s -= A[l]              # ⚠️ 여기만 % 가 없다
s += A[r % len(A)]
```
상한이 `3n`인 구조에서 `l`이 `2n`을 넘으면 IndexError다. 실측상 발생하지 않지만 **"왜 안전한지"가 코드에 없었다.** 개선본에서 `l % m`으로 대칭화.

**5. `[B]`의 "recall 곡선 그래프화"는 미완**

캘린더 08-09 항목은 *"k=50 EM 측정 + recall 곡선 그래프화 + README"* 였다. EM 측정과 README는 끝났지만 **그래프는 없다.** `data/eval/recall_curve.json`은 있고 `scripts/recall_curve.py`도 있는데 이미지 산출물이 레포에 없다. README도 표만 있고 `.png` 참조가 없다.
