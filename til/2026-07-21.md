## 배운 개념
- **도구 = 함수 + 스키마 + 매핑, 세 조각이 전부 맞아야 한다.** 함수만 있으면 LLM이 못 부르고,
  스키마만 있으면 실행이 안 되고, `TOOL_MAP`이 없으면 이름을 함수로 되돌릴 수 없다.
  `function.name`과 실제 함수명을 일치시켜 두면 `TOOL_MAP[name](**args)` 한 줄로 디스패치된다.
- **tool 메시지는 순서가 계약이다.** assistant의 `tool_calls` 메시지를 먼저 넣고
  그 다음에 같은 `tool_call_id`를 가진 tool 메시지를 넣어야 한다. 순서를 바꾸면
  API가 "응답할 대상이 없는 tool 결과"로 보고 거부한다. 대화 히스토리는 로그가 아니라 상태다.
- **description은 주석이 아니라 라우팅 로직이다.** LLM이 도구를 부를지 말지는 오직
  `description`으로 판단한다. "무엇을 반환하는지"(각 항목이 `[title] text`)와
  "언제 써야 하는지"(특정 엔티티/사건/주제의 사실 조회)를 둘 다 써야 호출률이 안정된다.
- **멀티홉 분해는 모델이 알아서 하지 않는다.** 프롬프트로 "한 번에 사실 하나"를 강제하지 않으면
  질문 전체를 검색어로 통째로 넣어 1홉 검색으로 끝나버린다. ReAct의 이점은
  루프 구조가 아니라 **분해된 검색어**에서 나온다.
- **종료 조건을 도구 호출 유무로 판정한다.** ReAct 루프의 종료는 텍스트 파싱이 아니라
  `if not msg.tool_calls` — function calling API에서는 이게 "Thought 끝, Answer 시작"의 신호다.

## 막힌 부분
- **도구 반환 타입을 뭘로 할지 헷갈렸다.** `retrieve_and_rerank`는 튜플 리스트를 주는데
  LLM은 str만 읽는다. "검색기 반환형"과 "도구 반환형"은 별개이고 그 사이 포맷팅이
  도구 래퍼의 존재 이유라는 걸 늦게 정리함. 도구는 로직이 아니라 **어댑터**다.
- **메시지 append 순서를 처음에 반대로 잡을 뻔했다.** tool 결과를 먼저 넣고 assistant를
  나중에 넣는 그림이 직관적으로 먼저 떠올랐다. 주석(`# assistant tool_call 먼저 (순서 중요)`)을
  남겨두긴 했지만, 왜 그런지(= tool 메시지는 특정 tool_call_id에 대한 **응답**이라 선행 호출이
  반드시 있어야 함)를 문장으로 붙여둬야 다음에 안 헷갈린다.
- **`chroma_index.ipynb`에 경로 버그가 남아 있다.** `open("..\data\corpus.json")` —
  Windows 역슬래시가 파이썬 문자열 이스케이프(`\d`)로 먹힌다. 같은 노트북 다른 셀은
  `"../data/qa.json"`으로 올바르게 되어 있어 일관성이 깨진 상태. 경로는 항상 `/` 또는
  `os.path.join`으로 통일할 것.
- **`run_agent`가 아직 손 테스트 1건(`qa[8]`)만 돌아본 상태.** 실패 케이스
