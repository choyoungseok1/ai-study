## 오늘 한 것
- `code/week16/delivery_boxes.py` — 프로그래머스 Lv2 "택배상자" (메인 벨트로 1..n 순서로 오는 상자를 원하는 `order`대로 트럭에 싣되, 차례가 아닌 상자는 LIFO 보조 벨트에 보관. 몇 개까지 실을 수 있는지 세기).
  - **메인 벨트 기준 루프** 채택: `for box in 1..n`으로 상자를 하나씩 스택에 push하고, `while stack and stack[-1] == order[idx]`로 실을 수 있는 만큼 연쇄 배출(`pop` + `answer/idx += 1`).
  - 시간 O(N) — 각 상자는 push 1회 / pop 1회뿐이라 분할상환 O(N)(단조 스택과 동일 논증). 공간 O(N)(역순 최악). 실측 N=10^6 랜덤 0.59s / 역순 0.73s.
  - 검증: 문제 예시 + 경계(역순 전체 배출, 순차 즉시 배출, `[3,1,2]→1`, `[1]→1`) 6개 케이스, 기대값은 손으로 세고 근거 주석으로 남김.

## 배운 개념
- **루프 기준 선택이 종료 조건을 없앤다**: 같은 문제를 (가) 메인 벨트 기준 vs (나) order 기준으로 짤 수 있는데, (가)를 고르면 "더 못 싣는" 상황에서 `while` 조건이 자동으로 거짓이 되고 남은 상자는 그냥 스택에 쌓이다 `for`가 끝난다. `answer`가 이미 정답이라 실패 감지·`break` 분기가 아예 필요 없다 → 예외를 처리하는 게 아니라 **예외가 생기지 않는 구조를 고르는 것**.
- **`if`가 아니라 `while`인 이유**: 상자 하나를 싣는 순간 스택 top이 다음 필요 번호와 맞아 **연달아** 배출될 수 있다. 한 번 싣고 또 실을 수 있는지 다시 봐야 하므로 반복이어야 한다. `if`면 `[4,3,...]`에서 3을 놓친다.
- **`answer`와 `idx`는 값이 같아도 의미가 다르다**: `answer`=실은 개수(결과), `idx`=order에서 지금 볼 위치(커서). 하나로 합치는 건 최적화가 아니라 가독성 손해 → 변수 의미 혼동 예방.

## 막힌 부분
- **`stack and`를 왜 앞에 두나**: 단락 평가. 스택이 비면 `stack[-1]`을 평가하지 않는다. 순서를 바꾸면 빈 스택에서 IndexError.
- **`order[idx]`의 idx 범위 초과가 왜 안 나는가(증명)**: idx는 pop할 때만 증가하고 pop은 push 개수를 못 넘는다 → idx ≤ n. idx == n이 되는 시점엔 스택이 비어 있어 `stack and`에서 먼저 걸린다. "우연히 안 터진다"가 아니라 **왜 안 터지는지 증명 가능**해야 한다(롤케이크 8/1 TIL의 "빈 오른쪽 vs 최소 1개 왼쪽" 증명과 같은 구조).
- **등록할 패턴**: "넣은 순서와 빼는 순서가 다른 문제" = 스택 + 조건 만족 시 `while` 연쇄 배출. 루프를 **입력(메인 벨트) 기준**으로 돌면 종료 조건이 저절로 해결된다.
