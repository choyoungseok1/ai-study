### 2. 측정 설계 — 나눌 수 없는 건 나누지 않았다

### 4. `context_precision.py` — TPD에 지수 백오프를 걸면 31초를 버린다

```python
msg = str(e)
if "per day" in msg or "TPD" in msg:
    raise RuntimeError(f"일일 토큰 한도 소진 — 재시도 무의미: {e}") from e
wait = 2 ** attempt
```

> *"⚠️ TPD(일일 한도)와 RPM(분당 한도)은 다르게 다뤄야 한다. RPM은 기다리면 풀리지만 TPD는 하루가 지나야 한다. **TPD에 지수 백오프를 걸면 31초를 버리고 똑같이 실패한다.**"*

`2^0+2^1+2^2+2^3+2^4 = 31`초. 숫자가 주석에 근거로 들어가 있다.

## 배운 개념

**1. 배율은 분자가 아니라 분모에서 조작된다**

44.7배 → 5.76배를 만든 건 Agentic의 개선이 아니라 **비교군의 측정 범위 정정**이다. "N배 빠르다/느리다"류 수치를 볼 때 물어야 할 것은 분자가 아니라 **분모가 무엇을 포함하는가**다. pure의 검색만 재면 0.06초인데 이건 실제 응답시간의 **1.5%**다. 이 분모로 나누면 어떤 시스템이든 수백 배 느려 보인다.

**2. 중앙값은 가법적이지 않다 — 내역의 합은 총합과 다르다**

```
rerank:  검색 7.20 + 생성 0.84 = 8.04  ≠  총합 중앙값 8.40  (0.36초 차이)
pure:    검색 0.06 + 생성 3.97 = 4.03  ≈  총합 중앙값 4.04  (0.01초)
```

각 구간의 중앙값을 따로 내면 **서로 다른 시행에서 온 값**이라 합이 총합 중앙값과 일치하지 않는다. 통계적으로 정상이지만, 표에 "내역"으로 나란히 쓰면 읽는 사람은 합이 맞을 거라 기대한다. pure는 오차가 안 보이고 rerank는 보인다. → [막힌 부분] 1번.

**3. "왜 느린가"는 구조 문제와 환경 문제로 갈린다**

> *"★ rerank와 pure는 **느린 이유가 정반대다.** rerank는 시간의 86%가 cross-encoder 재정렬이고 pure는 98%가 생성이다. **재정렬 비용은 로컬 CPU 때문이지 구조적인 것이 아니다.**"*

같은 "느리다"라도 pure의 98%(생성)는 어떤 하드웨어에서도 남고, rerank의 86%(재정렬)는 GPU를 붙이면 사라진다. **총 시간만 보면 rerank가 pure보다 2배 느리다는 결론에서 멈추는데, 분해하면 "이 2배는 환경 탓"이 나온다.**

**4. 대기 전략은 "풀리는 한도"와 "안 풀리는 한도"를 갈라야 한다**

RPM/TPM은 시간이 자원을 회복시키므로 백오프가 유효하다. TPD는 회복이 없으므로 백오프가 **비용만 쓰고 결과가 같다.** 재시도 로직 일반의 원칙 — *재시도가 상태를 바꾸는가*를 먼저 묻는다.

**5. 측정 불가는 측정값이 아니라 `None`으로 남긴다**

`retrieve=None, generate=None`. 0이나 total을 넣으면 나중에 평균·비율 계산에 조용히 섞인다. 코드에서도 `if r["retrieve"] is not None` 으로 걸러 출력한다.
