## 배운 개념
- **안 터지는 고장이 제일 위험하다**: Gemini는 tool_call마다 `extra_content.google.thought_signature`를 붙이는데, 이걸 빠뜨려도 요청은 **200으로 성공**한다. 에러 없이 조용히 품질만 떨어진다. → 터지는 고장은 발견되지만 안 터지는 고장은 배포된다. 어댑터의 역할은 필드를 표준형으로 '깎는' 게 아니라 **원본 보존을 명시적 책임으로 만드는 것**.
- **`raw`를 `model_dump()` 하지 않고 원본 객체로 든 이유**: ① dict 변환이 `extra_content`를 살려낼지 미검증이고 SDK 버전업에 조용히 깨질 수 있다. ② 리팩터 전 코드가 `messages.append(msg)`였으므로 **같은 객체를 넘기면 동작 불변이 구조적으로 보장**된다. 리팩터의 목표가 "기능 추가"가 아니라 "동작을 안 바꾸는 것"일 때 검증 부담을 줄이는 선택.
- **추상화의 경계는 "무엇을 모르게 할 것인가"로 정한다**: 루프가 몰라야 하는 것 = SDK 자료형, JSON 파싱, `tool_choice` 파라미터. 루프가 알아야 하는 것 = `text`가 있으면 최종답 / `tool_calls`가 있으면 계속. 그래서 `ChatResult` 필드가 딱 3개다.
- **누적합에서 앞에 `[0]`을 붙이는 것이 핵심**: 안 붙이면 `i == 0`에서 "뺄 값이 없는" 특수 케이스가 생겨 분기가 필요해진다. 0은 '빈 prefix'를 표현하는 패딩 → **예외를 처리하는 게 아니라 예외가 생기지 않게 만든다**(8/4 택배상자의 "루프 기준을 바꾸면 종료 조건이 사라진다"와 동일 발상).
- **`elements + elements[:-1]` (2n-1)이면 충분한 이유**: 최대 접근 인덱스 = `i + L - 1` = `(n-1) + (n-1)` = `2n-2`. `elements * 2`도 틀리진 않지만 원소 하나가 논다. 정확성이 아니라 정밀함의 문제.

## 막힌 부분
- **"accumulate가 복잡도를 낮춘다"는 오해를 정정**: `accumulate`는 누적합의 구현 수단일 뿐이고 롤링 방식과 **복잡도가 똑같이 `O(N^2)`**다. 차이는 상수(파이썬 for vs C 레벨 루프)뿐. `O(N^3)`→`O(N^2)`로 내려간 진짜 이유는 accumulate가 특별해서가 아니라 **`sum()` 재계산을 없앴기 때문**. → "복잡도가 낮다" ≠ "빠르다"를 계속 구분할 것.
- **`sum(ext[i:i+L])`이 상수가 아니다**: 한 줄이라 O(1)처럼 보이지만 슬라이싱이 새 리스트를 만들고(O(L)) 그걸 더한다(O(L)). 복잡도 사전 체크의 사각지대. v1이 채점을 통과한 건 `sum()`이 C 구현이라 상수가 작고 테스트가 최대 크기를 안 썼기 때문 — **"통과했다" ≠ "복잡도가 맞다"**.
- **`[:-1]`과 `[0]+`가 서로 맞물려 있다**: 최대 `i+length` = `(n-1)+n` = `2n-1` = `len(prefix_sums)-1`. 인덱스 상한이 딱 맞는 건 우연이 아니라 두 선택의 결과라, **하나만 바꾸면 깨진다**.
- **`provider = provider or default_provider()`를 쓰지 않은 이유**: retriever는 `or`로 두면서 provider는 `is None`으로 쓴 것이 일관성 없어 보이지만, provider 객체가 `__bool__`/`__len__`을 정의하면 falsy가 될 수 있다. retriever 쪽도 같은 위험이 있어 **다음에 통일할 것**(미해결).
